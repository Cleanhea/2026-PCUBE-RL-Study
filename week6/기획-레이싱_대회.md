# week6 — RacingBot Cup 기획서

> **한 줄 요약**: 동일한 차량·동일한 트랙 생성기 위에서, 참가자가 각자 설계한 ML-Agents 자율주행 에이전트로 **처음 보는 트랙을 얼마나 빠르고 안정적으로 도는지** 겨루는 솔로 타임어택 대회.

---

## 1. 왜 이 대회인가

week1~5에서 배운 것(관측 설계 · 보상 설계 · 하이퍼파라미터 · 센서 선택)을 **한 문제에 전부 쏟아붓는** 종합 과제입니다. 특히:

- **일반화**가 곧 점수 — 특정 트랙에 과적합하면 처음 보는 트랙에서 무너집니다
- **설계의 자유도가 곧 실력차** — 차량 물리는 모두 같으므로, 순위는 "무엇을 보게 했는가 / 무엇을 잘했다고 알려줬는가"에서 갈립니다
- 리더보드가 있으므로 **실험 → 측정 → 개선** 사이클을 자기 주도로 돌게 됩니다

---

## 2. 경기 개요

| 항목 | 내용 |
|---|---|
| 종목 | 솔로 타임어택 (차량 간 상호작용·추월·충돌 없음) |
| 차량 | 운영진 제공 `CarController` 1종 고정 (물리·성능 전원 동일) |
| 트랙 | 시드 기반 절차적 생성 (`TrackGenerator`) |
| 참가자가 만드는 것 | ML-Agents 에이전트 설계 + 학습 → `.onnx` 모델 |
| 평가 | 비공개 시드 트랙 주행 → 베이스라인 봇 대비 랩타임 |
| 기간 중 | 매일 갱신되는 비공개 시드로 자동 채점 → **리더보드 실시간 반영** |
| 결선 | 제출 마감 후, 완전 비공개 트랙에서 최종 주행 → 우승자 결정 |

## 3. 고정되는 것 vs 자유인 것

대회의 뼈대입니다. **"차는 똑같고, 뇌만 다르다"**.

| 영역 | 고정 (운영진 제공) | 자유 (참가자 설계) |
|---|---|---|
| 차량 물리 | 질량·엔진 토크·조향각·마찰·다운포스 | — |
| 행동 공간 | 연속 2차원 `[steer, throttle]` (`-1~1`) 또는 제공된 이산 매핑 | 둘 중 택 1 |
| 트랙 생성 | 생성기 알고리즘·난이도 파라미터 범위 | 학습에 쓸 시드·난이도 조합 |
| **관측** | 관측 **카탈로그**(제공되는 센서·항목 목록) | **어떤 걸 몇 개 켤지, 파라미터를 어떻게 줄지** |
| **보상** | — | **전부 자유** |
| **학습** | — | 알고리즘(PPO/SAC), 하이퍼파라미터, 커리큘럼, 학습 스텝, 네트워크 구조 전부 자유 |
| 추론 | ONNX + 인엔진 추론, 결정론 모드 | — |

> 보상과 학습 설정은 **학습 시점에만 존재**하고 평가에 개입하지 않으므로 제약이 전혀 없습니다.
> 관측만 카탈로그 방식인 이유는 4절에서 설명합니다.

## 4. 관측 — 자유도와 자동 채점을 동시에 잡는 방법

### 문제

참가자가 관측을 **C# 코드로 자유롭게** 짜면, 평가 하네스가 그 코드를 포함해 **매 제출마다 Unity를 다시 빌드**해야 합니다. 실시간 리더보드와 정면으로 충돌하고, 남의 코드를 평가 빌드에 넣는 순간 "트랙 데이터를 직접 읽는" 부정도 막을 수 없습니다.

### 해결 — 런타임 구성형 관측 카탈로그

참가자는 코드가 아니라 **`obs_config.json`** 을 제출하고, 평가 빌드가 이를 읽어 센서 스택을 런타임에 조립합니다.

```jsonc
{
  "sensors": [
    { "type": "ray3d", "name": "front",
      "raysPerDirection": 12, "maxAngle": 80, "rayLength": 60,
      "sphereRadius": 0.4, "verticalOffset": 0.6, "stacks": 2,
      "detectableTags": ["Track", "OffTrack"] },
    { "type": "ray3d", "name": "far",
      "raysPerDirection": 5, "maxAngle": 25, "rayLength": 150, "stacks": 1 }
  ],
  "vector": {
    "items": ["speed", "localVelocity", "angularVelocity", "steerAngle",
              "signedDistanceToCenterline", "trackWidth",
              "nextWaypointsLocal:5", "curvatureAhead:3", "lapProgress"],
    "stacks": 3
  }
}
```

**제공 센서**: `ray3d`(다중 세트 허용) · `camera`(해상도·grayscale·마운트 위치 조정 가능) · `grid`
**제공 벡터 항목**: 속도 / 로컬 속도 / 각속도 / 조향각 / 슬립각 / 센터라인 부호거리 / 트랙 폭 / 다음 K개 웨이포인트(로컬 좌표) / 전방 곡률 / 랩 진행도 / 이탈 플래그 / 마지막 체크포인트 경과 시간

### 카탈로그가 부족하면 — 추가 요청 창구

원하는 관측이 목록에 없으면 **관측 추가 요청 이슈**를 올리세요. 운영진이 검토해 카탈로그에 넣으면 **모든 참가자에게 동시에 열립니다**(공정성 유지). 단 카탈로그 **동결일(D-7) 이후에는 추가 없음**.

> 이 방식이면 참가자는 "레이를 몇 개, 몇 도로, 얼마나 멀리 쏠지", "카메라를 쓸지", "웨이포인트를 몇 개 볼지"를 전부 스스로 정하게 됩니다. 실제 설계 자유도의 대부분은 여기 있습니다.

## 5. 트랙 생성기 스펙

`com.unity.splines` 기반 (프로젝트에 이미 설치됨).

### 생성 절차

1. 시드 → 원형 루프 위 N개 제어점의 반경·각도를 난수 섭동
2. Catmull-Rom 스플라인으로 스무딩 → 최소 곡률 반경 위반 구간 재조정
3. 자기교차 검사 → 실패 시 재생성 (시드는 동일 결과를 보장해야 함)
4. 스플라인을 따라 도로 메시 생성 + 센터라인 + 체크포인트 자동 배치

### 난이도 파라미터 (시드로 샘플링되는 범위)

| 파라미터 | 범위(안) | 비고 |
|---|---|---|
| 총 길이 | 800 ~ 2,000 m | |
| 트랙 폭 | 6 ~ 12 m | 구간별 변동 허용 |
| 최소 곡률 반경 | 12 ~ 40 m | 작을수록 헤어핀 |
| 코너 수 | 8 ~ 20 | |
| 고저차 | 0 ~ 8 m | v2에서 도입 검토 |

### 트랙 밖

**물리적 벽은 두지 않습니다.** 트랙 밖은 마찰이 낮은 노면(잔디) — 나가면 느려지는 것이 자연스러운 페널티가 되고, "벽에 비비면서 코너 도는" 꼼수도 원천 차단됩니다.

### 도메인 랜덤화 (일반화 유도)

- **시각**(카메라 관측자용): 시간대·조명·건물 배치·노면 텍스처를 시드로 변경
- **물리**(옵션): 그립·질량 ±5% — 도입 시 **평가에서도 시드로 고정**해 결정론 유지

## 6. 평가 방식

### 주행 규칙

| 항목 | 규칙 |
|---|---|
| 랩 | 스탠딩 스타트 후 1랩 |
| 체크포인트 | 순서대로 전부 통과해야 랩 인정 (역주행·숏컷 차단) |
| 이탈 | 4륜이 트랙 밖인 상태가 **3초 지속되면 DNF** |
| 구조/리셋 | 없음. 나가면 스스로 복귀 |
| 타임아웃 | 베이스라인 봇 타임 × 3 |

### 점수

트랙 `t` 하나에 대해:

```
S_t = clamp(T_baseline / T_agent, 0, 2.0)      # 완주 시
S_t = 0                                         # DNF / 타임아웃
```

**총점 = 모든 트랙 `S_t`의 평균.**

- `T_baseline` = 운영진 제공 **규칙 기반 봇**(센터라인 추종 + 곡률 기반 감속)의 해당 트랙 기록
- 트랙 난이도가 자동 정규화되고, **`S = 1.0`이 "봇과 동급"** 이라는 직관적 기준선이 생깁니다
- DNF가 0점이므로 **"빠르지만 가끔 터지는" 정책보다 안정적인 정책이 유리** → 일반화 유도

**동점 처리**: ① 완주율 → ② 트랙별 점수 표준편차가 작은 쪽

### 결정론 확보 (같은 제출은 항상 같은 점수)

- `Time.fixedDeltaTime` 고정, 물리 시드 고정, 추론 `deterministic = true`
- ⚠️ **`-nographics`를 쓰면 카메라 센서가 검은 화면을 받습니다.** 평가 실행기는 GPU 러너 또는 가상 디스플레이(xvfb) 위에서 `-batchmode`만 사용할 것

## 7. 리더보드 — 대회 기간 중 실시간 랭킹

### 제출 규격

```
week6/submissions/<github-id>/
├── model.onnx           # ≤ 20MB
├── obs_config.json      # 4절 스키마
├── configuration.yaml   # 학습 설정 (재현·효율상 심사용)
└── meta.json            # 총 스텝, 학습 시간, 하드웨어, 한 줄 설명
```

PR로 제출합니다. 자기 디렉터리 외 파일을 건드리면 CI가 거부합니다.

### 파이프라인

```
PR 생성 ──> CI 스키마 검증 ──> 평가 빌드 실행(오늘의 비공개 시드 5개)
                                    │
                                    ├─> results/<id>.json 갱신
                                    └─> LEADERBOARD.md 재생성 + GitHub Pages 배포
```

- **반영 시간**: 제출 후 약 5~15분 (완전 실시간은 아님 — 표기도 그렇게 합니다)
- **매일 00:00 KST**: 새 시드 세트로 **전 제출물 일괄 재평가** → 어제 1위가 오늘 밀릴 수 있음

### 비공개 시드를 "숨긴 채로 재현 가능"하게

```
daily_seeds = HMAC(REPO_SECRET_SALT, YYYY-MM-DD) → 5개 시드
```

솔트는 GitHub Secrets에 둡니다. 참가자는 시드를 모르지만 운영진은 언제든 동일하게 재현할 수 있습니다.

| 시드 대역 | 용도 | 공개 |
|---|---|---|
| `0 ~ 99,999` | 학습·연습용 | 공개 |
| `1,000,000+` | 일일 리더보드 | 비공개 |
| 별도 | 결선 | 비공개 |

### 시드 탐침 방지

- **제출 1일 3회 제한** (같은 시드에 반복 제출해 맞춰가는 것 방지)
- 시드가 매일 바뀌므로 리더보드 상위권 = 이미 일반화 성능의 대리 지표

### 참가자 로컬 검증

동일한 평가 빌드를 **공개 시드용으로 배포**합니다. 제출 전에 로컬에서 같은 절차·같은 점수식으로 자기 채점이 가능해야 합니다.

```bash
RacingEval.exe --model model.onnx --obs obs_config.json --seeds 12,34,56 --out result.json
```

### 인프라 선택지

| 안 | 구성 | 평가 |
|---|---|---|
| **A (추천)** | 운영진 PC를 GitHub Actions **self-hosted runner**로 등록 (Windows + GPU) | 카메라 센서 렌더 OK, 빠름. PC가 켜져 있어야 함 |
| B | `ubuntu-latest` + Linux 빌드 + xvfb | 무료·항상 가동. 렌더 세팅이 까다로움 |
| C | 운영진이 배치 스크립트 수동 실행 (1일 1회) | 폴백. "실시간" 포기 |

## 8. 결선

1. 제출 마감 (D-day 23:59)
2. **비공개 결선 트랙 12개** — 생성기 시드 10개 + **손으로 만든 트랙 2개**
3. 스터디 시간에 **화면 공유로 라이브 실행** (관전 포인트: 헤어핀·연속 코너에서 갈림)
4. 총점 순 시상

> 손으로 만든 2개는 생성기 분포 밖(OOD) 트랙입니다 — 극단적 헤어핀, 긴 고속 직선 후 급코너 등. **여기서 무너지지 않는 에이전트가 진짜 일반화된 것**이라 보고, 별도 부문으로도 시상합니다.

## 12. 리스크

| 리스크 | 대응 |
|---|---|
| 평가 결과가 실행마다 달라짐 | fixedDeltaTime·시드·결정론 추론 고정, 동일 제출 2회 실행해 검증하는 CI 테스트 |

| 셀프호스티드 러너 다운 | 폴백으로 수동 배치 실행 공지 |
